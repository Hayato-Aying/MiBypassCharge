## 1. 为什么改：v1.1 在 K70 上根本跑不起来

v1.1 的候选节点表（8 条）在这台机器上**一条都不存在**，`detect` 必然 FAIL。实测：

| v1.1 期望的节点                         | K70 实际                                  |
| ---------------------------------- | --------------------------------------- |
| `qcom-battery/restricted_charging` | 不存在（有 `restrict_chg`）                   |
| `battery/input_suspend` 等 6 条      | 全部不存在                                   |
| —                                  | 真实节点在 `/sys/class/qcom-battery/`（102 个） |

而且即使换成真实节点，**`input_suspend` 也不是旁路**：实测写 1 后 `status` 变 `Discharging`、电流 `+0.46 A`（手机转吃电池）、VBUS 从 8.18 V 掉到 5.14 V。用户看到的就是"开了旁路，电量还在掉、温度没降"。

## 2. 新机制：走官方停充位 `smart_chg`

安全中心「导航断充保护」（`md/c.java` → `ChargeProtectionUtils`）最终是：

```java
IMiCharge.setMiChargePath("smart_chg", "0x" + hex((level << 16) | flag))
//  navigation: flag = 0x3      always: flag = 0x11
//  关闭导航：0x2
```

落到节点 `/sys/class/qcom-battery/smart_chg`。掩码布局（实测）：

| 位      | 值             | 含义                 |
| ------ | ------------- | ------------------ |
| bit0   | `0x1`         | 停充生效               |
| bit1   | `0x2`         | 导航模式               |
| bit4   | `0x10`        | 全局/常态化保护（本机能力位不支持） |
| bit5   | `0x20`        | 另一开关               |
| bit7   | `0x80`        | 无线静音充电             |
| 高 16 位 | `level << 16` | 停充电量               |

**实测（2026-11-17，插 PD 充电器）**

| 写入                   | 结果                                                                   |
| -------------------- | -------------------------------------------------------------------- |
| `0x500003`（80%）在 52% | 继续充电（没到点）                                                            |
| `0x340003`（52%）在 52% | **立刻停充**：`current=0`、`VBUS=9.07V`、`usb.online=1`、Scene 显示 **0.00 W** |
| 拔线 → 3 s → 插回        | **仍停在旁路**，电量不涨 → 驱动自己保持，不需要重申                                        |
| `0x2` → 等 8 s → `0`  | 恢复充电（这一步不能省，只写 `0` 有时解不掉）                                            |

## 3. 行为变化（和 v1.1 对比）

| 维度         | v1.1                            | v1.2                                           |
| ---------- | ------------------------------- | ---------------------------------------------- |
| 执行层        | 写 `input_suspend` 等单值节点         | 写 `smart_chg` 掩码（驱动级）                          |
| 生效判定       | 只看 `status` 字                   | **只看 `current_now`**（`status` 会滞后显示 Charging）  |
| 稳态维持       | 每 2 tick 无条件重写                  | 不重写；只有"明显又充上了"连续 2 次才补写                        |
| 拔电         | 逻辑易抖动                           | 主动清停充位，下次插上从充电开始                               |
| 恢复充电       | 写一次 0                           | `0x2`→等 6 s→`0`，并用电流确认，失败再补一次                  |
| 卸载         | 复位一堆不存在的节点                      | 两步复位 `smart_chg` + `input_suspend` + 老节点       |
| 通知按钮"恢复充电" | 把 `MODE` 改成 `force_off`（永久退出自动） | 走 `resume`：恢复充电后**回到自动**                       |
| 兜底         | 无                               | `smart_chg` 不生效时退到 `input_suspend`（标注"断充，非旁路"） |

## 5. 已知限制

1. **重启会复位**：sysfs 不落盘，开机后由 `service.sh` 拉起守护、按当前电量重新写一次。
2. **`0x11`（全局保护位）未验证**：本机 `persist.vendor.smartchg=6` 只声明 bit1/bit2，所以默认用 `3`（导航位），不要随便改 `SMART_MODE=17`。
3. **读回值不可信**：写 `0x340003` 节点读回 `2`（驱动归一化），只能用电流判断。
4. **恢复充电有 10–20 秒延迟**：PD 要重新协商，期间电流会乱跳，属正常。
5. 只针对 K70 验证过；其他机型需先跑 `bg-ctl.sh detect`。

## 6. 升级 / 回退

- 升级：KernelSU 里直接刷 v1.2（模块 id 相同，配置保留）。
- 回退：刷回 v1.1 **前**先执行 `sh /data/adb/modules/bypass_guard/bin/bg-ctl.sh resume` 并确认在充电，或者直接卸载模块（`uninstall.sh` 会复位）。

## 8. 打包 / 刷机前检查清单（每次打包都要过一遍）

1. **脚本必须是 LF 换行**。v1.2 打包时踩过一次：用 Python 补丁脚本改完 `bg-daemon.sh` / `bg-ctl.sh`  
   后变成 CRLF，设备上 mksh 直接报 `bin/bg-daemon.sh[9]: : inaccessible or not found`，守护起不来。  
   打包前跑：
   ```bash
   python -c "import zipfile;z=zipfile.ZipFile('MiBypassCharge-v1.2.zip');print([n for n in z.namelist() if n.endswith(('.sh','.prop','.js')) and b'\r\n' in z.read(n)])"
   # 必须是 []
   ```
2. 设备上对**解压后的实际文件**做语法校验：`for f in bin/*.sh *.sh; do sh -n $f; done`。
3. `module.prop` 的 `id` 必须和模块目录名一致（`bypass_guard`），否则 KSU 不认。
4. 壳 App 用 `adb install -r -d -g` 先单独试装一次，确认能装、能起、不崩。
5. 确认签名还是 `src/bg.jks`（与旧版同签名才能覆盖升级）。

## 10. v1.5 / v1.6：省电重做（单轮 189ms → 50ms，空闲间隔 3s → 60s）

### 10.1 实测出来的真凶：不是 fork 多，是每次读 sysfs 都要 exec

在 K70 上（HZ=100，各跑 100 次取均值）：

| 读法                                           | 成本        |
| -------------------------------------------- | --------- |
| `cat battery/capacity`                       | 34 ms     |
| `cat battery/uevent`（一次读全部）                  | 72 ms     |
| `cat /dev/null`（纯 exec 基准）                   | 26 ms     |
| **`read -r v < battery/capacity`（shell 内建）** | **3 ms**  |
| **`read` 6 个属性**                             | **10 ms** |

结论：**`cat` 的 26~34ms 里，绝大部分只是「fork + exec 一个 toybox 二进制」**，  
跟读了几个字节无关。所以 v1.2~~v1.4 每轮 6~~7 次 `cat` ≈ 190ms，  
3 秒一轮就是 **6~7% 的单核占用**，而且还一直在把 CPU 从 idle 里叫醒。

v1.5 把全部读取改成 shell 内建 `read < 文件`（只走 open/read/close，不 fork）：

|        | 每轮成本                                               |
| ------ | -------------------------------------------------- |
| v1.4.5 | 189 ms                                             |
| v1.6   | 19 ms（读取） + 38 ms（`sleep` 本身的 exec，绕不开）≈ **50 ms** |

### 10.2 轮询间隔按场景自适应

`smart_chg` 是驱动级的「充到 X 停」，状态由驱动保持。**插着电的时候驱动自己就会按它执行，  
守护根本不需要守着**——这是能把空闲间隔拉长的前提。

| 场景         | 间隔                |
| ---------- | ----------------- |
| 插电、离阈值 ≤3% | **3 s**（要精确停在阈值上） |
| 已在旁路中      | **9 s**（看补电、看拔线）  |
| 插电、离阈值还远   | **15 s**          |
| 没插电 / 功能关闭 | **60 s**          |

配套改动：**拔电时不再清停充位**，而是把它对齐成「充到当前阈值停」。  
这样下次插上电，驱动自己就会在阈值处停，不用等守护醒来。

### 10.3 抄了开源项目 bypass-charger v10.3.5 的四条工程实践

对照 `github.com/QiZhi-yi/bypass-charger`（v10.3.5）。该仓库未声明标准开源协议（GitHub 显示
`NOASSERTION`），因此在此明确标注来源：下面标"已抄"的四条是实质参考，非独立原创。

| 项           | bypass-charger                                        | 我们                   |
| ----------- | ----------------------------------------------------- | -------------------- |
| 停充节点        | `soc_limit`（新平台）/ `smart_night`·`night_charging`（老平台） | `smart_chg` 高 16 位   |
| K70 上能做到多精确 | **无 `soc_limit`**，退化到 `night_charging`，最低只能 80%       | 任意电量（1~100%）         |
| 单轮成本        | 6 次 `cat` ≈ 180 ms                                    | 6 次内建 `read` ≈ 12 ms |
| 轮询          | 插电 15 s / 空闲 60 s                                     | 3 / 9 / 15 / 60 s 四档 |
| **并发写节点**   | **flock 串行化**                                         | **已抄**               |
| **改配置立即生效** | **SIGUSR1 打断 sleep**                                  | **已抄**               |
| 单实例         | mkdir 原子锁                                             | supervisor 单一父进程     |
| KSU 禁用检测    | 有                                                     | 已抄                   |
| 退出/崩溃复位充电   | 有                                                     | 已抄（`trap EXIT`）      |
| 阈值变更后重新裁决   | 有                                                     | 已抄                   |

它记录过一起真实事故，值得单独说：**守护和 WebUI 并发写同一个充电节点，  
会触发厂商充电驱动内部死锁，进程卡在 D 状态、杀不掉、插电不充**。  
所以现在所有节点写入都走 `flock -n`（非阻塞，拿不到锁就放弃这一轮），锁文件  
`/data/adb/bypass_guard/.node_lock`。

### 10.4 顺手修掉的问题

- **守护启动时误判**：新加的「阈值变更重裁决」在 `LAST_EN` 初始为空时会把启动当成"用户改了阈值"，  
  79%（阈值 80）被判成"该充电"，清了停充位 → 79↔80 反复横跳。已改成启动时用当前阈值初始化。
- **「恢复充电」按钮点了没用**：原来切回 `auto`，而 auto 下"电量 ≥ 阈值就停"，  
  80% 时点它会被下一轮立刻又停掉。改成 `force_off`（一直充），充满 100% 由守护自动切回 `auto`。
- **`pkill -f` 会杀掉执行它的 shell**：命令行里出现同样的字符串就会自匹配。  
  部署脚本改成按 pid 文件 + `/proc/<pid>/cmdline` 校验命令行，pgrep 模式用 `[.]` 转义。
- **`echo "-154000"` 在 mksh 里被当成选项**，吐空串 → 功率恒为 0。改成 `printf`。
- **32 位算术溢出**：K70 的 sh 是 32 位整数（`4119000*403000` 溢出成 `2099623744`），  
  功率改成先降到 mV/mA 再乘。
- **WebUI 长按能选中所有文字**：`*` 全局 `user-select:none`，只放行输入框和日志。

### 10.5 省电效果

| 场景          | v1.4.5          | v1.6                |         |
| ----------- | --------------- | ------------------- | ------- |
| 每轮成本        | 189 ms          | 50 ms               | ÷3.8    |
| 未插电（8 小时睡眠） | 3 s/轮 → 7.6% 单核 | 60 s/轮 → **0.083%** | **÷92** |
| 插电待机        | 7.6%            | 15 s/轮 → 0.33%      | ÷23     |
| 旁路中         | 7.6%            | 9 s/轮 → 0.56%       | ÷14     |
| 临界（3% 内）    | 7.6%            | 3 s/轮 → 1.7%        | ÷4.5    |

按一晚 8 小时闲置 + 白天 16 小时插电估算，守护占用的 CPU 从 **约 1.8 核·小时/天**  
降到 **约 0.06 核·小时/天**。

> 换算是按 CPU 时间算的，实际待机耗电还要算唤醒本身的代价（退出 idle、PMIC 唤醒），  
> 所以真实收益只会比这个比例更大，不会更小。

## 11. v1.6.1 / v1.6.2：两个真实事故

### 11.1 「关了开关还是不充电」—— 停充位没人松

v1.6 为了省电，做了一件事：**拔电时不清 `smart_chg`，而是把它留成「充到阈值停」**，  
这样插上电后驱动自己就会照做，守护可以睡 60 秒。

代价是在 15:40 踩了一个坑：

```
用户拔电 → 守护写入 smart_chg = 0x500003(80)
用户插上 → 充到 79%
用户关掉「旁路供电」开关
→ 守护此时 BP=0，而"清停充位"只在 BP 从 1 变 0 时才发生
→ 没有任何人去写 smart_chg → 79% 卡住不充电，而且开关怎么关都没用
```

**修法两步**：

1. 取消「拔电保留」这个优化，拔电照旧清 0（回到 v1.5 的行为）；
2. 增加一道保险：**只要 `ENABLED != 1` 或 `MODE = force_off`，每轮都确认停充位是松开的**，  
   不管 `BP` 是多少。

### 11.2 SIGUSR1 唤醒不可靠

`kill -USR1` 唤醒「睡着的守护」在真机上时灵时不灵：实测改回 `ENABLED=1` 之后  
守护一直没反应。查 `/proc/<pid>/wchan` 发现它卡在 `__do_sys_rt_sigsuspend` ——  
mksh 在 `wait` 子进程时用 sigsuspend 等，信号会被屏蔽挂起。

**改成不依赖信号**：`bg-ctl.sh set` 在改完配置后，**自己按新配置校正一次停充位**  
（`ENABLED`/`MODE`/两个阈值这几个键才做）。信号仍然发，但只是"顺手"，醒不醒都行。

实测：

| 操作               | 生效时间                     |
| ---------------- | ------------------------ |
| 阈值 85 → 90（应继续充） | **4 秒**松开停充位，12 秒恢复 1.5A |
| 阈值 90 → 85（应停充）  | **2 秒**写停充位，4 秒电流归零      |
| 关开关 ENABLED=0    | **2 秒**松开，12 秒恢复 2.45A   |

改阈值时按「当前电量 vs 新阈值」直接裁决，不走滞回区 —— 否则把阈值调到当前电量之上，  
会卡在滞回区里一直不充。

### v1.7.2 根因深挖与验收（整合自原《热修复报告-v1.7.2》）

> 原独立报告已并入本文，以下保留最有价值的根因分析与实测数据。

**开关颜色不同步的真正根因（关键发现）**

现象：点开关后滑块滑到另一侧，但背景仍是蓝色，要等几秒后 toast 弹出才变黑。
原因是两个视觉属性走了**不同的渲染管线**：

| 属性 | 渲染路径 | 受主线程阻塞影响 |
|---|---|---|
| 滑块位移 `transform` | GPU 合成层 | 否，立刻动 |
| 背景色 `background` | 主线程 paint | 是，被冻结 |

KSU 的 `exec` 在部分版本**同步阻塞 JS 主线程**。阻塞期间主线程 paint 发不出去，
所以背景卡在蓝色、滑块先动；命令跑完、主线程解锁（正是 toast 弹出时）背景才补上变黑。
这也说明 `nextFrame()`（先让出一帧再发命令）对这个问题是无效的——让出后 exec 照样阻塞。

修法：把蓝色背景从"直接改 `background`"改为独立 `::before` 覆盖层 + `opacity` 过渡
（`will-change:opacity`）。`opacity` 与 `transform` 同属合成层属性，不受主线程阻塞，
滑块与背景即可严格同步。真机确认："正常了"。

**watch 多实例根因（两处叠加）**

排查中发现后台堆了 4 个 `bg-watch`（重复监听 logcat 白费电）：
1. `bg-watch.sh` 用 `trap 'rm -rf $LOCK' EXIT` 释放锁，但 `logcat | while read` 会 fork
   子 shell，子 shell **继承了这个 trap**——它一退出就删掉父进程仍持有的锁，下一个实例得以启动。
2. `start_all()` 里主动 `rm -rf .watch.lock`，使 `watch_start` 的去重判断失效，每次 boot 多起一个。

修法：锁释放加 pid 校验（只有持锁者本人退出才删）；`watch_start` 改用进程表 `watch_pids` 去重；
`start_all` 不再删锁。真机验证：清→0、开→2（1 主 1 管道子）、反复开关 3 轮仍 2、重复 boot 仍 2。

覆盖基线进程、守护自愈、WATCH 开关与不堆积、巡检间隔、老配置补字段与 `force_off→auto` 迁移、
